# ابدأ من هنا — Sleepee Label & Printing Hardened Candidate v1.4

**الحالة: نسخة مرشحة للمراجعة — ليست إصدار إنتاج معتمدًا.**

هذه الحزمة أُعيد تركيبها انطلاقًا من `SLEEPEE_PLATFORM_PHASE_10_18_UNIFIED_v1.0(4).zip`، ثم طُبقت فوقها التغييرات والملفات الإضافية الموجودة في `SLEEPEE_PLATFORM_INTEGRATION_CANDIDATE_v1.0.zip`. لم يُحذف أي ملف من خط أساس 10–18 في عملية المقارنة. تمت إضافة مخطط معماري جديد لتوجيه المراجعة والبناء في Google AI Studio.

## إعادة البناء التي تمت في هذه الحزمة

- تم اعتماد ZIP المراحل 10–18 أساسًا للمقارنة، وليس استبداله بحزمة مرشحة دون توثيق.
- كل ملفات خط الأساس الـ108 موجودة في حزمة التكامل السابقة؛ لم يكن هناك ملف من خط الأساس غائبًا من تلك الحزمة.
- تضمنت حزمة التكامل السابقة 26 ملفًا إضافيًا و15 ملفًا مشتركًا بتغيّر في المحتوى.
- تم إنشاء مخطط معماري عربي جديد بصيغتي Markdown وWord، وإضافته إلى الحزمة.
- أزيل مبدّل الدور التجريبي الذي كان يسمح بتغيير دور المستخدم داخل حالة الواجهة؛ هذا تعديل على الكود، لكن لا يثبت بمفرده صحة RLS أو صلاحيات Supabase الحية.

- صُححت شاشة فحص قاعدة البيانات لتعرض ستة فحوص أساسية فقط، وأزيلت أرقام التغطية الثابتة وتعليمات تشغيل SQL التاريخي تلقائيًا.

## أحدث تصحيحات الملصقات والطباعة — Candidate v1.3

- أصبح التخطيط الافتراضي يستجيب لأبعاد القالب الفعلية، مع تحقق هندسي يمنع حفظ/نشر العناصر الواقعة خارج حدود الملصق.
- يدعم المصمم المقاسات `100×50` و`100×80` و`100×100` والمقاسات المخصصة الموجبة بالأعداد الصحيحة.
- مركز الطباعة يطلب اختيار قالب نشط ومنشور صراحة، ويعرض الاسم والفئة والمقاس والإصدار، ولا يستخدم اختيارًا تلقائيًا لـ`100×100`.
- يتم حفظ لقطة من أبعاد القالب وعناصره وإصداره ضمن بيانات أمر الطباعة، لمنع اعتماد التنفيذ اللاحق على قالب تغيّر بعد إنشاء الأمر.
- إعادة الطباعة تنشئ أمرًا في الانتظار ولا تكتب سجل طباعة ناجحًا قبل التنفيذ الفعلي.
- تكامل Zebra/Browser Print ورندر الباركود الفيزيائي لا يزالان غير معتمدين؛ واجهة التنفيذ تظل fail-closed ولا تدّعي نجاحًا ماديًا.
- تقرير التفاصيل: `docs/integration/LABEL_AND_PRINTING_HARDENING_REPORT_AR.md`.

## ما لم يتم بعد

- لم يُرفع هذا الإصدار إلى مستودع GitHub جديد، ولم يُربط بعد بـGoogle AI Studio.
- لم يُنشأ أو يُضبط مشروع Supabase الجديد.
- `npm run build` و`npm run lint` لم يثبت نجاحهما في بيئة نظيفة؛ التبعيات/lockfile تحتاج معالجة داخل بيئة متصلة ومعتمدة.
- لم يتم التحقق من مخطط Supabase أو RPC أو RLS أو Storage أو Realtime في بيئة حية.
- لم تُختبر طابعة Zebra ZD220 فعليًا.
- ما زالت تعارضات مرجعية وتجارية موضحة في المخطط تحتاج إلى قرار أو تحقق ميداني.

## قاعدة الأمان

هذه حزمة مصدر للمراجعة. لا تنفذ `archive/legacy_sql/schema.sql` أو `archive/legacy_sql/supabase-schema.sql`، ولا تنفذ `SLEEPEE_PHASE_10_18_UNIFIED_MIGRATION.sql` أو الملف المقترح لهندسة التصنيع تلقائيًا. حتى على مشروع Supabase جديد، يجب أن يراجع مخطط التأسيس والـmigrations ويعتمدا قبل التنفيذ. لا تضف أسرارًا إلى المستودع ولا تنقل بيانات عملاء حقيقية إلى بيئة التطوير.

**الهدف التالي:** رفع الحزمة إلى مستودع GitHub خاص جديد، ثم استيرادها في مساحة Google AI Studio جديدة للمراجعة، وبعدها إعداد Supabase جديد ومعزول وفق المخطط وبوابات القبول.
