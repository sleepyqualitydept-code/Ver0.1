# تسليم Sleepee إلى GitHub وGoogle AI Studio — النسخة المعاد بناؤها

## ترتيب الاستخدام

1. أنشئ مستودع GitHub خاصًا جديدًا لهذه النسخة، وفق قرار المالك؛ اترك `sh0` والنسخة السابقة كما هما.
2. ارفع محتويات ZIP إلى جذر المستودع بعد فك الضغط؛ لا ترفع ZIP نفسه فقط. احتفظ بالمرجعية والوثائق كما هي، ولا تضع ملفات Excel الخام التي تحتوي معلومات تشغيل/تقييم داخل مستودع عام.
3. افتح `docs/reference/Sleepee_Architecture_Development_Blueprint_v1.0_DRAFT_AR.md` أولًا داخل Google AI Studio واطلب مراجعة معمارية وجردًا فقط قبل أن تسمح بتغييرات كود إضافية.
4. ارفع/استورد المستودع والفرع الصحيحين إلى مساحة Google AI Studio الجديدة. لا تفترض أن رفع ZIP إلى المحادثة أنشأ مزامنة GitHub أو ربطًا تلقائيًا.
5. احفظ أول commit وسمِّ الفرع بوضوح كنسخة مراجعة، واحتفظ ببصمة ZIP.

## بيئة Supabase الجديدة

- أنشئ مشروع Supabase جديدًا ومعزولًا لهذه النسخة فقط، ولا تمس المشروع/البيئة القديمة.
- لا تنقل بيانات عملاء أو فواتير أو ضمانات حقيقية إلى البيئة الجديدة دون قرار منفصل وخطة حماية.
- لا تنفذ ملفات SQL التاريخية أو الترحيلات المجمعة تلقائيًا، حتى لو كانت قاعدة البيانات الجديدة فارغة. راجع SQL وتأكد من اتساقه مع المرجعية والواجهات والعقود قبل التنفيذ.
- لا يُرفع إلى GitHub إلا `.env.example` بعناصر فارغة. في Secrets/Environment اضبط `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY`. لا تضع Service Role Key في الواجهة مطلقًا.

## تعليمات المراجعة للأداة

- اقرأ المخطط المعماري والمرجعية الأصلية وملحقات المالك قبل لمس الكود.
- لا تعِد كتابة المشروع من الصفر ولا تستبدل المسارات الموجودة دون مقارنة.
- أخرج تقريرًا يوضح الملفات والمكونات وعقود API/SQL والفجوات الأمنية وتعارضات الأدوار/الحالات.
- لا تضف Firebase/Firestore أو backend آخر أو بيانات ثابتة.
- لا تشغّل SQL ولا تصدر شهادة نجاح دون دليل. نفذ تعديلات صغيرة وأرفق diff ونتائج الاختبارات الحقيقية.

## فحوص البناء

بعد تثبيت نظيف للتبعيات وتوليد lockfile من مدير الحزم المعتمد، شغّل `npm run lint` و`npm run build`. يجب إصلاح الأخطاء وتسجيل النتيجة. وجود `package.json` أو نجاح فحص استيرادات فقط لا يثبت نجاح البناء.

## بوابات قبل الإطلاق

- تأسيس schema ومراجعة RLS/RPC/Storage/Realtime على المشروع الجديد من خلال SQL معتمد وقابل للمراجعة.
- اختبارات Phase 09: التفعيل والتكرار وثبات snapshot وسجل الأحداث والخصوصية والصلاحيات.
- اختبارات مسار الإنتاج والدفعات والأرقام التسلسلية و`Partially Completed`.
- إقرار دورة BOM/Routing والبيانات المصدرية لكل موديل وخط.
- اعتماد الملصق واختبار Zebra ZD220 فعليًا؛ لا تسجل print success قبل استجابة فعلية.
- إصدار ZIP وبصمة SHA-256 بعد إغلاق العوائق الحرجة وموافقة المالك.

**لا توجد مزامنة GitHub أو Supabase أو Google AI Studio تمت تلقائيًا بمجرد إعداد هذه الوثيقة.**
