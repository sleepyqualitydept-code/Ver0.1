## 1. الغرض وحالة الوثيقة

تجمع هذه الوثيقة نموذج التشغيل المستهدف واحتياجات تجربة المستخدم المسترجعة من المحادثة القديمة، وتربطها بالمرجعية الأصلية وملحق المراجعة. وهي مسودة تنظيمية لا تمثل اعتمادًا نهائيًا للنطاق أو إذنًا بالتنفيذ.


| ترتيب السلطة — المرجعية الأصلية Sleepee_Single_Source_Of_Truth_v1.0 أولًا؛ ثم قيود التقنية والنطاق؛ ثم توضيحات المالك الموثقة كتعديل منفصل عند تغيير/توسيع المرجعية؛ ثم ملفات التنفيذ كأدلة فقط. |

## 2. قواعد غير قابلة للتجاوز

- لا حذف لمتطلبات أو إعادة تسمية للعلامات والموديلات والفئات والأدوار ومسارات العمل وأرقامها دون موافقة صريحة.

- التقنية: React + TypeScript + Vite؛ Supabase PostgreSQL وAuth وRLS وStorage وRPC وRealtime فقط.

- ممنوع Firebase/Firestore أو قواعد بيانات بديلة أو LocalStorage/IndexedDB كمخزن أساسي أو mock/static/in-memory data كمصدر تشغيلي.

- لا إضافة ERP أو CRM أو محاسبة/تكاليف كنظام مستقل أو HR/Payroll أو مشتريات أو Warehouse ERP أو Vendor Portal أو POS أو E-Commerce.

- لا reset أو drop/recreate لمشروع Supabase الحالي؛ لا migration قبل المقارنة والنسخة الاحتياطية والموافقة.

- لا شهادة لمرحلة أو ميزة أو بيئة حية دون دليل تحقق فعلي؛ يجب التمييز بين CODE-VERIFIED وDATABASE-VERIFIED وLIVE-VERIFIED وNOT VERIFIED.

## 5. معيار تجربة مركز التشغيل

يجب ألا تكون الصفحة الافتراضية مجرد جدول CRUD. يبدأ كل مركز بملخص عملي، وحالات تستلزم تدخلًا، وإجراءات سريعة، وعمليات حديثة، وبحث، ثم التفاصيل والجدول عند الحاجة.

- Header: الشعار الرسمي، اسم النظام، المستخدم والأدوار، مركز إشعارات، الوضع الليلي/النهاري، التحكم بالحجم، البحث، إعدادات الحساب.

- Footer: سياسة الضمان والخصوصية والتواصل والعنوان والحقوق وسنة النظام، مع عدم نشر بيانات تواصل غير مؤكدة.

- Role-based home/dashboard: تخصيص المحتوى حسب الدور الفعلي دون اختراع صلاحيات جديدة.

- Global search: أرقام التسلسل والدفعات وأوامر الإنتاج والعميل والهاتف والفاتورة والضمان وحالة الخدمة ضمن الصلاحيات.

- Quick actions: تقتصر على إجراءات مسموحة في حالة السجل الحالية، وتمنع تجاوز الموافقات أو انتقالات الحالة.

- Notification Center: إشعارات داخل التطبيق مطلوبة؛ WhatsApp والبريد يعتمدان على مزود وإعدادات معتمدة لم تُحدد بعد.

- Barcode/QR-first: دعم الماسح كمدخل لوحة مفاتيح حيث يلائم تدفق العمل، دون اشتراط إدخال الرقم التسلسلي يدويًا.


## 6. مركز الإنتاج والتصنيع — تجربة المستخدم المستهدفة


### 6.1 وضعا التشغيل المسترجعان


| الوضع | المسار المرشح | حالة الاعتماد |

| --- | --- | --- |

| Quick Production | اختيار منتج ومقاس وكمية → إنشاء أمر إنتاج → إنشاء دفعة → توليد الأرقام التسلسلية → إنشاء Print Jobs → مركز الطباعة. | متطلب مسترجع من المحادثة؛ يحتاج تفصيل شروط كل انتقال قبل التنفيذ. |

| Manual / Advanced Production Wizard | أمر إنتاج → مراجعة/اختيار BOM وإصداره → Routing/Production Version → دفعة → أرقام تسلسلية → قالب → طباعة → إكمال. | متطلب مسترجع؛ مخطط التصميم والتفاصيل لم تعتمد بعد. |



Auto Progression مقترح عند نجاح التحقق من شروط المرحلة. يجب السماح بالرجوع للمراجعة دون إخفاء السجل التاريخي، ويجب أن تكون شروط الانتقال صريحة لا مجرد انتقال واجهة.


### 6.2 الدمج الظاهر والفصل الداخلي

تظهر وظائف الإنتاج والتسلسل والطباعة وتصميم الملصقات كتدفق واحد داخل مركز الإنتاج، بينما تبقى الخدمات البرمجية ومسؤولياتها مفصولة داخليًا. وكذلك تجمع وظائف الضمان وخدمة العملاء والاستبدال في مركز تجربة عميل واحد دون دمج الجداول في كيان واحد.


## 7. التقارير والتحليلات وجودة البيانات

- مخرجات تشغيلية قابلة للتتبع: كميات مخططة ومنفذة، تقدم الأوامر، حالات الدفعات والأرقام والطباعة، وحالات الضمان والخدمة والاستبدال.

- تصدير CSV وXLSX وJSON وPDF بحسب التقرير، وبيانات منظمة/موثقة للتكامل التحليلي الخارجي. لا وعد بتكامل مباشر مع كل أداة قبل تحديد واختبار النطاق.

- Data Quality checks مرشحة: منتج بلا BOM، موديل بلا مقاس/تركيب، منتج فعال بلا Routing، Serial بلا Batch، Batch بلا أمر إنتاج، Print Job بلا قالب، بيانات ناقصة أو تكرارات تستحق المراجعة.

- Saved datasets مفهومة وواضحة المصدر؛ لا تستخدم أي عينة ثابتة أو سجلات تجريبية كمصدر تشغيلي.

- Genealogy يربط Serial بالمنتج ونسخة BOM/Routing وأمر الإنتاج والدفعة والطباعة ثم البيع/الضمان والخدمة والاستبدال، بقدر ما تسمح به البيانات الفعلية.


## 8. الإدارة والصلاحيات

أسماء الأدوار الأصلية: Administrator، Production Manager، Production Operator، Printing Operator، Customer Service User، Warranty Manager، Read Only User. التنفيذ في ZIP يستخدم بدائل لبعض الأسماء؛ لا تغير أو RLS قبل اعتماد Role Mapping رسمي. تفضيل المالك أن يحمل الموظف أكثر من دور يسجل كمتطلب يحتاج مطابقة مع المخطط والسياسات الحالية.


## 9. الإشعارات والأصول والملفات

- أصول الشعار والصور والعلامات والرموز في Supabase Storage، مع صلاحيات واضحة وعدم استخدام صور وهمية كمصدر تشغيلي.

- دلاء التخزين الأصلية: labels وservice وwarranty؛ يجب مراجعة الحالة الحية والسياسات قبل التغيير.

- الروابط/الملفات الخاصة لا تصبح عامة افتراضيًا؛ فصل ملفات الخدمة والفواتير والمرفقات عن المعلومات العامة.

- WhatsApp والبريد: لا مزود ولا أسرار في المستودع قبل قرار منفصل.
