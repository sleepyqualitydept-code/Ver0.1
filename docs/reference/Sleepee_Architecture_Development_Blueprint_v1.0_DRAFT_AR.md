# SLEEPEE — المخطط المعماري وخطة البناء الموحدة

**معرّف الوثيقة:** `SLEEPEE-ADB-001`  
**الإصدار:** `v1.0`  
**الحالة:** مسودة للمراجعة والاعتماد — ليست تصريحًا للنشر أو لتغيير قاعدة البيانات  
**تاريخ الإعداد:** 10 أكتوبر 2026  
**المشروع:** Sleepee Manufacturing, Warranty & Customer Service Platform  
**المرجعية الحاكمة:** `Sleepee_Single_Source_Of_Truth_v1.0`  
**خط أساس الكود:** `SLEEPEE_PLATFORM_PHASE_10_18_UNIFIED_v1.0(4).zip`  
**ملفات التحسين للمطابقة:** `SLEEPEE_PLATFORM_INTEGRATION_CANDIDATE_v1.0.zip`

> **الغرض:** هذه الوثيقة هي دليل المراجعة المعمارية والتعليمات التنفيذية الذي يجب قراءته قبل فحص الكود أو تعديله في Google AI Studio. وهي وثيقة مكملة؛ لا تستبدل المرجعية الأصلية ولا تمنح موافقة تلقائية على تغييرها.

## 1. الغرض وحدود الاستخدام

تضع هذه الوثيقة ترتيبًا واحدًا لبناء النسخة التالية انطلاقًا من خط أساس المراحل 10–18، مع الاستفادة من تحسينات الواجهة والتكامل والوثائق التي جُمعت في حزمة التكامل. الهدف هو منع إعادة البناء من الصفر، ومنع ضياع أعمال سابقة، ومنع اعتبار ملفات SQL أو تقارير قديمة دليلًا على أن البيئة الحية متوافقة.

هذه الوثيقة تخدم أربعة أغراض:

1. توجيه فحص البنية والكود قبل التنفيذ في Google AI Studio.
2. تعريف تجربة المستخدم المستهدفة وطبقات التطبيق ومسؤولية كل طبقة.
3. ترتيب التنفيذ والتحقق والقبول على مراحل صغيرة قابلة للمراجعة.
4. تسجيل التعارضات التي تمنع قرارًا آمنًا، دون اختراع معلومات لحلها.

**الحالة الحالية:** مخطط معماري مقترح للمراجعة. لا يُعتبر موافقة على ترحيل قاعدة البيانات أو إطلاق التطبيق للإنتاج. يجب أن يعتمد المالك هذه الوثيقة وأي تعديل تجاري/تشغيلي قبل أن تصبح مرجعًا تنفيذيًا ملزمًا.

## 2. ترتيب المرجعيات والسلطة

عند التعارض، اتبع الترتيب التالي ولا تحل التعارض بالحدس:

1. **المرجعية التجارية الأصلية:** `Sleepee_Single_Source_Of_Truth_v1.0`، وبالأخص MASTER REFERENCE SPECIFICATION VERSION 1.0. يجب أن تبقى دون تعديل.
2. **التكنولوجيا والنطاق المجمّدان:** React + TypeScript + Vite، وSupabase فقط للخدمات الخلفية وقاعدة البيانات والمصادقة والسياسات والتخزين وRPC وRealtime.
3. **توضيحات المالك الموثقة:** ملحق توضيحات المالك ومراجعة المتطلبات v1.2. تُسجل أي إضافة/تغيير كملحق مستقل بإصدار واضح، ولا تعدّل النص الأصلي بصمت.
4. **هذه الوثيقة:** مخطط للبناء والترتيب الفني؛ لا تملك سلطة لتغيير قواعد العمل الأصلية.
5. **الكود وملفات SQL والتقارير:** أدلة على ما يوجد في الملفات فقط، وليست دليلًا على نشره في قاعدة Supabase الحية أو نجاحه.

إذا لم تؤكد الملفات قاعدة أو قيمة أو حالة، سجّلها `BLOCKED / SPECIFICATION GAP`. لا تُكمل اعتمادًا على تخمين أو بيانات افتراضية.

### 2.1 بيئة إعادة البناء الجديدة — توجيه مالك مستقل

اتجاه العمل الحالي هو إنشاء بيئة تطوير جديدة ومعزولة لهذه النسخة: مستودع GitHub خاص جديد، ومشروع Supabase جديد، ومساحة عمل Google AI Studio جديدة. هذا توجيه خاص ببيئة النسخة المرشحة ولا يغيّر المرجعية الأصلية أو قواعد العمل، ولا يعني حذف أو إعادة ضبط أو تعديل البيئة السابقة.

- تظل النسخة القديمة وبياناتها خارج نطاق التعديل، وتستخدم كمرجع تاريخي عند الحاجة فقط.
- يجب ألا تُنسخ بيانات عملاء/فواتير/ضمان حقيقية أو أسرار من البيئة القديمة إلى بيئة التطوير الجديدة دون قرار منفصل وآمن.
- إنشاء مشروع Supabase جديد لا يبرر تشغيل ملفات SQL التاريخية. يجب بناء خطة schema/migrations قابلة للمراجعة ومطابقة للمرجعية، مع فصل تأسيس قاعدة فارغة عن ترحيلات التحديث.
- لا يُعتبر المشروع الجديد جاهزًا بمجرد إنشائه؛ يلزم إثبات الهوية، وضبط Auth/RLS/Storage/RPC/Realtime، وتثبيت التبعيات، وإكمال اختبارات القبول.

## 3. القواعد غير القابلة للتجاوز

- عدم حذف أي متطلب أو إعادة تسمية العلامات أو الموديلات أو الفئات أو قواعد الضمان أو تنسيقات الأرقام أو حالات العمل دون موافقة صريحة.
- عدم بدء مشروع بديل من الصفر؛ حافظ على كود وخبرات المراحل الموجودة، وقم بتعديلات صغيرة قابلة للمقارنة.
- لا Firebase ولا Firestore ولا MongoDB ولا MySQL ولا SQLite ولا Airtable ولا backend بديل.
- لا `localStorage` أو `sessionStorage` أو `IndexedDB` أو JSON أو مصفوفات ثابتة كمصدر بيانات تشغيلي. تخزين حالة عرض مؤقتة لا يجعلها قاعدة بيانات؛ يجب أن تكون البيانات التشغيلية من Supabase.
- لا سجلات تجريبية أو fake/mock/demo data في مسارات التشغيل.
- لا ERP ولا CRM ولا محاسبة/تكاليف ولا HR/Payroll ولا مشتريات ولا Warehouse ERP ولا بوابة موردين ولا POS ولا تجارة إلكترونية.
- لا تشغيل لملفات SQL التاريخية أو ترحيل مقترح تلقائيًا.
- لا `DROP`, `TRUNCATE`, إعادة إنشاء أو تصفير قاعدة البيانات. لا Migration قبل جرد حي ونسخة احتياطية قابلة للتحقق ومقارنة وموافقة صريحة.
- لا مفاتيح أسرار في الكود أو GitHub. الواجهة تستخدم فقط متغيرات `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY`; لا تضع `service_role` key في الواجهة.
- لا اعتبار للطباعة ناجحة إلا بعد استجابة حقيقية من مسار الطباعة المعتمد؛ ولا شهادة لأي مرحلة دون دليل الاختبار الفعلي.

## 4. اتجاه تجربة المستخدم المستهدفة

التنظيم المقترح للعرض هو مساحات عمل رئيسية واضحة، مع بقاء المكوّنات والمسارات الداخلية منفصلة برمجيًا. هذا تنظيم للواجهة، وليس إضافة إلى نطاق العمل التجاري.

| المساحة | الوظائف التي تظهر للمستخدم | الحدود |
|---|---|---|
| الرئيسية / Dashboard | مؤشرات حية، تقدم الأوامر، حالة الطباعة، قضايا الخدمة والاستبدال والتنبيهات | كل رقم يجب أن يأتي من بيانات Supabase الفعلية وبصلاحيات المستخدم |
| الإنتاج والتصنيع | بيانات المنتج، مواصفات الموديل، BOM، Routing، تخطيط الإنتاج، أوامر الإنتاج، الدفعات، التسلسل، تصميم الملصق والطباعة | تُستخدم إصدارات معتمدة عندما يعتمد مسار الاعتماد؛ لا تُخترع BOM أو Routing افتراضية |
| تجربة العميل: الضمان والخدمة | ملف العميل، الرقم التسلسلي، الضمان، حالات الخدمة، الإصلاح، الاستبدال، التعويض إن اعتمدت سياسته، المرفقات، السجل الزمني والتدقيق | لا دمج غير مبرر للجداول؛ كل انتقال وصلاحية يجب أن يكون محددًا |
| التقارير والتحليلات | تقارير الإنتاج والضمان والخدمة والاستبدال والطباعة والإدارة، التصدير، فحوص جودة البيانات | لا تدّعِ اكتمال dataset أو API قبل تنفيذها واختبارها |
| الإدارة | المستخدمون والأدوار والإعدادات والقوالب والأصول والبيانات الرئيسية وسجلات التدقيق | الأدوار مصدرها موثوق على الخادم؛ لا تبديل دور من الواجهة لأغراض الإنتاج |
| التحقق العام `/verify` | تحقق محدود بالرقم التسلسلي أو QR أو الباركود ومعلومات المنتج/الضمان المسموح بها | Public read-only؛ لا تعرض بيانات شخصية أو مستندات خاصة |

**قاعدة تصميم:** يمكن أن يبقى `/production/*` و`/serialization/*` و`/printing/*` و`/label-designer/*` وغيرها مسارات داخلية مستقلة حتى لو ظهرت للمستخدم كتدفق إنتاج واحد. الدمج البصري لا يعني دمج مسؤوليات الكود أو جداول قاعدة البيانات.

## 5. البنية المعمارية المستهدفة

### 5.1 طبقات التطبيق

| الطبقة | المسؤولية | ضوابط القبول |
|---|---|---|
| واجهة المستخدم / App Shell | التنقل، اللغة العربية RTL والإنجليزية، الثيم، البحث، الإشعارات، الأطر العامة | لا تتجاوز الصلاحيات أو تنفّذ قواعد عمل تجارية داخل عناصر العرض فقط |
| مساحات العمل / Feature UI | شاشات الإنتاج، الهندسة، الملصقات، الطباعة، الضمان، خدمة العملاء، الاستبدال، التقارير والإدارة | كل شاشة حالة مستخدم واضحة؛ لا تُظهر بيانات غير متاحة في Supabase |
| API / Domain Services | استدعاءات API typed وتنسيق العقود والتدفقات | لا بيانات ثابتة كبديل؛ لا fallback يغير معنى العملية عند فشل RPC |
| Supabase Client | اتصال المصادقة والبيانات والـRPC والتخزين والـRealtime | استخدام متغيرات البيئة المعتمدة فقط؛ معالجة أخطاء الاتصال بوضوح |
| PostgreSQL + RPC + RLS | المخطط العلائقي، القيود، الدوال الذرية، الصلاحيات وسلامة المعاملة | الخادم هو حد الأمان؛ كل تغيير حساس يراجع داخل RLS/RPC |
| Supabase Storage | الصور والقوالب والمرفقات وفق الصلاحيات | الحفاظ على الدلاء الحالية `labels`, `service`, `warranty` ومراجعة الحالة الحية قبل أي تغيير |
| الاختبارات والأدلة | بناء نظيف، اختبارات عقود/أدوار/تدفقات، تحقق حي واختبار الطابعة | نشر نتيجة فعلية لكل اختبار؛ لا استنتاج من وجود الملف فقط |

### 5.2 حدود مسؤوليات المجالات

- **Master Data:** الفئات والعلامات والموديلات والمقاسات وأنواع المنتجات؛ المصدر التشغيلي Supabase فقط.
- **Product Engineering:** مواصفات الموديل، BOM ونسخ BOM، Routing ونسخ Routing، النظام التصنيعي والخط/الماكينة، مراجع المصادر. أي جداول جديدة تبقى اقتراحًا حتى مراجعة المخطط الحي.
- **Production:** التخطيط، أوامر الإنتاج، الموافقات، الدفعات، التسلسل والتتبع.
- **Serialization:** إصدار الرقم الفريد، عدم إعادة استخدامه، وربط تاريخه بالإنتاج والدفعة والطباعة والبيع والضمان والخدمة والاستبدال.
- **Printing & Label Design:** القوالب والأبعاد والأصول وPrint Jobs والتاريخ. يختلف تصميم/Preview القالب عن تأكيد نجاح الطباعة الفعلية.
- **Warranty:** السياسة والتفعيل والتحقق وسجل الأحداث. تفعيل الضمان يمر عبر RPC المعتمد، لا كتابة مباشرة من عميل الويب إلى جدول التفعيلات.
- **Customer Service / Replacement:** حالات الخدمة والمرفقات والموافقات وربط المنتج القديم والجديد والتاريخ الكامل.
- **Reporting & Audit:** الاستعلام عن البيانات المصرح بها وإظهار المصدر والتاريخ؛ لا تخزين مجموعة تقارير ثابتة كبديل للمصدر.

### 5.3 فصل التنفيذ عن البيانات

وجود واجهة لـBOM أو Routing لا يعني أن جداولها نُشرت. ملف `docs/proposed-migrations/20261010_additive_manufacturing_engineering.sql` اقتراح مراجعة خارج مسار الترحيلات النشطة. لا يُنقل إلى مسار نشط ولا يُنفذ قبل مقارنة أسماء الجداول والأعمدة والدوال والسياسات بالمخطط الحي ومراجعة أثره.

## 6. عقود العمل التي يجب حفظها

### 6.1 الإنتاج والدفعات

حالات أمر الإنتاج في المرجعية الأصلية:

`Draft → Planned → Approved → In Production → Partially Completed → Completed → Cancelled`

حالات الدفعة:

`Created → Serialized → Printed → Completed`

لا يسمح للواجهة بتجاوز الموافقة المطلوبة. يجب أن تحدد عقود قاعدة البيانات صلاحيات كل انتقال وآثاره؛ حالة `Partially Completed` تحتاج مطابقة بين المرجعية وTypeScript وقيود قاعدة البيانات قبل اعتبار التدفق مكتملًا.

### 6.2 أرقام التتبع

- أمر الإنتاج: `ORD-YYYY-XXXXXX`
- الدفعة: `BAT-YYYY-XXXXXX`
- الرقم التسلسلي: `SLP-YYYY-XXXXXXXX`

الرقم التسلسلي فريد عالميًا، ولا يُعاد استخدامه أو تصفيره، ويُبحث عنه من واجهات البحث المسموح بها. يجب الحفاظ على تاريخ الإنتاج والدفعة والطباعة والضمان والخدمة والاستبدال، وعدم حذف الأحداث التاريخية بصمت.

### 6.3 الضمان وPhase 09

- بداية الضمان: تاريخ فاتورة المستهلك، لا فاتورة الموزع ولا النقل الداخلي.
- يمكن أن تتضمن الفاتورة الواحدة أكثر من رقم تسلسلي.
- التفعيل عبر RPC المعتمد مع منع التفعيل المكرر، والتحقق من حالة الرقم التسلسلي وشروط التفعيل.
- تُحفظ مدة الضمان وتاريخ انتهائه كلقطة ثابتة عند التفعيل؛ تعديل سياسة لاحقة لا يغير التفعيلات السابقة.
- يجب المحافظة على عقد Phase 09 ووظائفه المعتمدة (`activate_warranty`/عقد الأحداث المعتمد) وعدم إضافة مسار كتابة مباشر كحل بديل.
- السياسة الحالية المسجلة في وثيقة تصميم خدمة العملاء: كل المراتب بكل العلامات والموديلات 10 سنوات؛ المخدات والخداديات ومراتب التطرية سنتان. تسمح المرجعية الأصلية بمدة قابلة للتهيئة من 1 إلى 15 سنة وبهرمية Category Default ثم Brand Override ثم Model Override. أي سياسة مستقبلية مختلفة يجب اعتمادها دون إعادة كتابة snapshots السابقة.
- التاريخ الذي توثقه ملفات المشروع على أنه شهادة سابقة لا يساوي إعادة اختبار حي حديث؛ يجب تسجيل حالة `LIVE-VERIFIED` فقط بعد الاختبار على البيئة المستهدفة.

### 6.4 الخدمة والاستبدال والتعويض

أنواع حالات الخدمة الأصلية: `Inquiry`, `Complaint`, `Warranty`, `Maintenance`, `Replacement`, `Follow-Up`, `Other`.

سير الخدمة الأصلي: `Open → Assigned → In Progress → Resolved → Closed`.

سير الاستبدال الأصلي: `Requested → Under Review → Approved → Replacement Issued → Completed`.

يجب الحفاظ على الرقم الأصلي وسجل الضمان والخدمة والعميل عند الاستبدال، وربط الرقم الجديد دون إلغاء تاريخ الأصل. مسار التعويض مذكور كمتطلب مسترجع لكنه يحتاج سياسة وموافقات معتمدة؛ لا يُحوّل إلى نظام محاسبي ولا تُخترع له مبالغ أو حدود.

### 6.5 التصنيع وBOM وRouting

الأقسام الفعلية المسجلة:

1. قسم السلك.
2. قسم التطريز والتفصيل.
3. قسم التنجيد والتجميع.
4. قسم التيب.
5. قسم التغليف.

المسار والزمن يختلفان حسب موديل المرتبة، نظام التصنيع، الوجه/الوجهين، Pillow Top، نوع السوست والمكونات، وخط أو ماكينة التشكيل. لا تستخدم مسارًا عامًا لجميع الموديلات.

مصادر البيانات المشار إليها في الملحق:

- `Models BOM.xlsx`: مكونات الموديل وأكواد الخامات والأبعاد والكميات، ويتضمن ورقة وقت تشغيل.
- `وقت التشغيل.xlsx`: ملف وقت تشغيل مستقل يجب مطابقته مع الورقة المضمنة، دون استبدال تلقائي.
- `توضيح الطبقات والحشو الداخلي.xlsx`: مصدر تكوين الطبقات والهندسة وليس بديلًا عن BOM لكل موديل.
- `كل المواد الخام مصنع السست.xlsx` و`EGYP RM FOR EDRAKY 23 MARCH 2025.xlsx`: مراجع أكواد خامات، لا تسمح بإعادة تسمية الأكواد تلقائيًا.

لا تُقسّم قيمة زمن إجمالية إلى أزمنة الأقسام الخمسة بالتخمين. مثال المالك الخاص بـInfinity (57 دقيقة مع دورة تشمل 9 مراتب على طاولات التنجيد/التجميع التسع) ليس قاعدة عامة لكل موديل. التعارض بين 9 طاولات للتنجيد/التجميع و10 طاولات إجماليًا، وتعارض Rrstcalm بعرض 78/80 سم، والقيمة 150 دون اسم موديل في ملف وقت التشغيل، تظل نقاطًا مفتوحة حتى التوثيق.

### 6.6 الملصقات والطباعة

- المقاسات الأصلية: `100×50 mm` و`100×100 mm`؛ والتحسينات المجمعة تتضمن `100×80 mm` وأبعادًا مخصصة باعتبارها طلبًا يحتاج تثبيتًا واعتمادًا قبل الإنتاج.
- الحقول المرشحة: الشعار، العلامة، الموديل، المقاس، الرقم التسلسلي، الباركود، QR، الضمان الفعلي، الدفعة وتاريخ الإنتاج حسب عقد البيانات.
- الطابعة المعرفة في المرجعية: Zebra ZD220 عبر USB. يجب التحقق من Browser Print/renderer الفعلي والطباعة المادية قبل تسجيل نجاح.
- تصميم الملصق الموجود ليس تصميمًا نهائيًا معتمدًا. الموافقة البصرية ومحتوى الملصق واختبار القياس والقراءة شروط مستقلة.

## 7. الهوية والصلاحيات والأمان

### 7.1 مشكلة أسماء الأدوار

تسرد المرجعية الأصلية الأدوار: `Administrator`, `Production Manager`, `Production Operator`, `Printing Operator`, `Customer Service User`, `Warranty Manager`, `Read Only User`. وتستخدم أجزاء من الكود وSQL أسماء أخرى مثل `Warranty Officer`, `Customer Service Agent`, `Service Manager`. هذا تعارض حقيقي يجب أن يُحسم بجدول ربط معتمد قبل تغيير Auth أو RLS أو صلاحيات المسارات. لا تغيّر الأسماء بصمت ولا تعتبر اختلاف الاسم مجرد اختلاف عرض.

سجل المالك تفضيل السماح للموظف بحمل أكثر من دور؛ يتطلب ذلك التحقق من نموذج البيانات الحي وعقود الصلاحيات قبل التنفيذ. لا تكفي قيمة `role` واحدة في ذاكرة React لإثبات صلاحية المستخدم في قاعدة البيانات.

### 7.2 ضوابط إلزامية

- أزل/امنع مبدل الأدوار التجريبي من واجهة المستخدم غير المخصصة للاختبار؛ لا يجوز تبديل دور مستخدم فعلي من العميل.
- RLS وRPC على Supabase هما حد الأمان الفعلي؛ حماية React مجرد تجربة تنقل ولا تحل محل حماية الخادم.
- مراجعة المصادقة وإنشاء الملف الشخصي وحالات عدم وجود دور؛ لا تُمنح صلاحيات افتراضية عند غياب تعيين موثوق.
- التحقق العام Public Read-only لا يعرض رقم قومي أو هاتفًا أو عنوانًا أو مرفقات أو بيانات عميل. البحث بالهاتف أو الفاتورة يحتاج قرار خصوصية وتحققًا مناسبًا وRPC معتمدًا.
- تخزين الأصول والمرفقات عبر Supabase Storage بسياسات وصول واضحة. لا تجعل ملفات الخدمة أو الضمان عامة افتراضيًا.

## 8. سياسة التعامل مع الكود وملفات SQL

1. ابدأ من حزمة المراحل 10–18، واجعل تحسينات حزمة التكامل طبقة مطابقة وتعديلات موثقة فوقها؛ لا تُسقط ملفات المصدر بلا تسجيل.
2. لا تدمج حزمة Phase 09 مختلفة فوق هذه الشجرة نسخًا عشوائيًا.
3. ملفا `archive/legacy_sql/schema.sql` و`archive/legacy_sql/supabase-schema.sql` أدلة تاريخية فقط. لا تنفذهما على قاعدة قائمة.
4. ملف `SLEEPEE_PHASE_10_18_UNIFIED_MIGRATION.sql` مرشح تاريخي غير مصدّق على المخطط الحي. لا يُفترض أنه جاهز للتنفيذ لمجرد وجوده.
5. ملف هندسة التصنيع المقترح يبقى داخل `docs/proposed-migrations/` حتى يراجع ويعتمد.
6. قبل أي ترحيل: إثبات هوية المشروع، تصدير/نسخة احتياطية، جرد للجداول والأعمدة والقيود والفهارس والدوال/RPC والسياسات والدلاء وRealtime، فرق موثق، خطة رجوع، تجربة على بيئة غير إنتاجية إن توفرت، ثم موافقة صريحة.
7. إذا اختلف الكود مع المخطط الحي أو المرجعية، سجّل الفرق وأوقف الجزء المعتمد عليه حتى يقرّر المالك.

## 9. خطة التنفيذ المقترحة وبوابات القبول

### Gate 0 — تثبيت خط الأساس

- حفظ ZIP الأصلي وبصمته.
- تسجيل اسم الفرع وCommit SHA للمستودع الذي سيُستخدم عند إنشاء المستودع الجديد.
- جرد الملفات والمقارنة مع حزمة التحسينات، وتوثيق الملفات الجديدة والمتغيرة والمحذوفة.
- تضمين هذا المخطط والمرجعية المحمولة في جذر/مجلد الوثائق بشكل يسهل الوصول إليه.

**شرط القبول:** لا يوجد أي فقد غير موثق من خط الأساس؛ المرجعية الأصلية موجودة بنسخة مطابقة.

### Gate 1 — المراجعة المعمارية والأمنية

- تثبيت ترتيب المرجعيات.
- إزالة مبدل الدور غير الآمن من الواجهة العادية.
- توثيق تضارب الأدوار، وحالة `Partially Completed`، وغياب lockfile، وتعليمات النشر المتعارضة، وفجوات Supabase الحية.
- فحص التقنيات الممنوعة والبيانات الثابتة والأسرار في الشجرة النشطة.

**شرط القبول:** تقرير فجوات واضح؛ لا ادعاء اكتمال الأمن أو قاعدة البيانات.

### Gate 2 — بيئة بناء قابلة للتكرار

- تثبيت التبعيات في بيئة متصلة ومعتمدة، وتحديد مدير حزم واحد.
- إنشاء lockfile فعلي من حل التبعيات؛ لا يُكتب يدويًا.
- تشغيل `npm run lint` و`npm run build` وتسجيل الخرج.
- إصلاح أخطاء TypeScript/build بالأدلة، مع اختبارات لمنع regression.

**شرط القبول:** أوامر البناء والفحص تنجح في بيئة نظيفة؛ وإلا تبقى الحالة `BLOCKED`.

### Gate 3 — مراجعة عقد Supabase

- فحص schema/Auth/RLS/RPC/Storage/Realtime قراءة فقط.
- مقارنة عقود `activate_warranty` وسجل الأحداث والتوليد والطباعة مع المخطط الفعلي.
- مراجعة سياسات الأدوار المعتمدة قبل تعديل أي policy.
- مراجعة الترحيلات المقترحة في فرق منفصل واختبارها في بيئة آمنة.

**شرط القبول:** مخطط حي موثق ونسخة احتياطية قابلة للتحقق واختبارات RLS/RPC مع أدلة.

### Gate 4 — إتمام تدفقات التشغيل

- استكمال BOM/Routing وإصدارات الإنتاج بعد اعتماد دورة المسودات/الموافقة/السريان.
- إتمام Quick Production وManual/Advanced Wizard دون اختصارات تتجاوز الموافقات.
- مطابقة `Partially Completed` والتاريخ التسلسلي مع العقود المعتمدة.
- استكمال تجربة العميل الموحدة وتحديد دورة التعويض ونقل الملكية قبل التنفيذ.

**شرط القبول:** سيناريوهات قبول موثقة من البداية إلى النهاية، ببيانات اختبار معتمدة داخل بيئة الاختبار وليس بيانات ثابتة في الكود.

### Gate 5 — الطباعة والتحقق الميداني

- اعتماد تصميم الملصق والمحتوى.
- اختبار المقاسات الفعلية مع Zebra ZD220 وBrowser Print/renderer المعتمد.
- اختبار الباركود/QR، حدود القص، إعادة الطباعة، فشل الاتصال، وعدم تسجيل نجاح كاذب.

**شرط القبول:** سجل اختبار مادي موثق وصورة/عينة موافق عليها.

### Gate 6 — الإصدار

- مراجعة نهائية للفرق، سجل الاختبارات، نتيجة التدقيق الأمني، وملخص الترحيلات المعتمدة.
- إصدار ZIP جديد وبصمة SHA-256 وحالة واضحة.
- حفظ النسخة السابقة وإمكانية الرجوع.

**شرط القبول:** موافقة المالك على الإصدار وعدم وجود بنود حرجة مفتوحة تمنع الاستخدام المقصود.

## 10. مصفوفة تحقق الإصدار

| المجال | الدليل المطلوب | الحالة في الحزمة الحالية |
|---|---|---|
| سلامة خط الأساس | تقرير مقارنة ملفية وبصمات | تم تجميع ملفات الحزمتين؛ يجب إرفاق تقرير إعادة البناء النهائي |
| بناء Vite | `npm run build` من تثبيت نظيف | غير متحقق في بيئة المراجعة الحالية بسبب غياب التبعيات |
| TypeScript/Lint | `npm run lint` / `npm run typecheck` | غير متحقق حتى تثبيت التبعيات |
| مخطط Supabase حي | تصدير schema وفهرس RPC/RLS/Storage/Realtime | غير متحقق؛ لم يحدث اتصال حي في هذه المراجعة |
| ضمان Phase 09 | حالات نجاح/تكرار/لقطة/صلاحيات على قاعدة اختبار | الشهادة السابقة موثقة تاريخيًا؛ إعادة الاختبار الحي مطلوبة |
| BOM/Routing | تدقيق بيانات مصدر لكل موديل وخط وإصدار | مسودات واجهة ومخطط مقترح؛ لا اعتماد للبيانات أو الهجرة بعد |
| الطباعة | اختبار Zebra ZD220 فعلي | لم يُنفذ |
| الخصوصية العامة | اختبار منع تسرب بيانات شخصية | يحتاج اختبارًا حيًا على RPC والبوابة |
| GitHub/Google AI Studio | المستودع والفرع والمزامنة | لم يتم الرفع أو الربط من هذه الحزمة |

## 11. القرارات المعلّقة التي لا يجوز تخمينها

- جدول الربط الرسمي بين أسماء الأدوار الأصلية وأسماء الأدوار الموجودة في الكود/SQL، وكيفية دعم تعدد الأدوار.
- عقد حالة `Partially Completed` بين المرجعية وTypeScript وقيود قاعدة البيانات.
- دورة اعتماد BOM/Routing ونسخة الإنتاج وتاريخ سريانها.
- المسار والزمن ومخرجات الدورة لكل موديل/خط، وتوزيع 9 طاولات تنجيد/تجميع مقابل 10 طاولات إنتاج إجمالًا.
- تعارض عرض Rrstcalm: 78 أم 80 سم، وأي قياسات/أكواد مكونات متعارضة أخرى.
- قيمة `150` تحت February في صف بلا اسم موديل في ملف وقت التشغيل.
- سياسة SH الموثقة بصورة متعارضة بشأن مدة/تكرار التعليمات، ونص الضمان العام النهائي.
- سياسة التعويض وموافقاته وحدوده، وقواعد نقل الملكية والمنتجات المفقودة/المتلفة/الملغاة/المرتجعة/المنقولة.
- مزود البريد/WhatsApp وقنوات الإشعار وأسرارها، إذا تم اعتمادها.
- اعتماد تصميم الملصق النهائي ومحتواه وسياسته لبيانات QR.
- التحقق من بنية Supabase الحالية وتوافر جميع الدوال والسياسات والدلاء اللازمة.

## 12. تعليمات مباشرة لـGoogle AI Studio أو أي أداة بناء

انسخ التعليمات التالية كما هي عند بدء مراجعة/بناء الحزمة:

> أنت تعمل على مشروع Sleepee القائم، وليس مشروعًا جديدًا. اقرأ أولًا `docs/reference/Sleepee_Architecture_Development_Blueprint_v1.0_DRAFT_AR.md` ثم المرجعية المحمولة `docs/reference/Sleepee_Single_Source_Of_Truth_v1.0_Portable_Reference.md` ثم ملحقات المالك ومصفوفة الفجوات. المرجعية الأصلية هي السلطة التجارية النهائية ولا يجوز تعديلها. افحص الملفات الفعلية قبل اقتراح تغيير، واعرض خطة فروق صغيرة قبل التنفيذ. استخدم React + TypeScript + Vite وSupabase فقط. لا تضف Firebase أو backend/قاعدة بيانات أخرى، ولا تستخدم بيانات ثابتة كمصدر تشغيلي. لا تنفذ أو تنقل ملفات SQL إلى مسار ترحيلات نشطة قبل جرد قاعدة Supabase الحية والنسخ الاحتياطي والمقارنة والموافقة. حافظ على عقود Phase 09 ولقطات الضمان وسجل التتبع. لا تسجل نجاح طباعة قبل تأكيد مادي. لا تخترع قاعدة أو قيمة لحل تعارض؛ سجّلها BLOCKED. بعد كل دفعة تعديل، قدّم الملفات المتغيرة وسبب كل تغيير وأوامر التحقق التي شُغلت ونتائجها الحقيقية. لا تدّعِ build أو RLS أو قاعدة بيانات حية ناجحة إذا لم تُختبر فعليًا.

## 13. ما المطلوب إرفاقه بكل دفعة عمل

كل دفعة تعديل يجب أن تنتج:

1. قائمة الملفات التي تغيرت أو أضيفت وسبب كل تغيير.
2. ربط كل متطلب بملف/دليل التنفيذ، مع `PASS / FAIL / PARTIAL / NOT VERIFIED / BLOCKED`.
3. نتائج الأوامر الفعلية: الأمر، البيئة، النتيجة، وأي سبب فشل.
4. قائمة التعارضات المفتوحة ولماذا لم تُحسم.
5. تأكيد عدم تنفيذ SQL أو إجراء تغيير حي غير معتمد.
6. ملف فرق/patch أو سجل يمكن مراجعته والرجوع عنه.
